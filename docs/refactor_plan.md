# 项目重构实施计划

## 目标

在保持现有任务接口与已确认行为的前提下，降低飞控控制、行为树节点、ROS 通信和工具界面的耦合，集中重复逻辑，使后续新增任务、调整控制策略和定位问题更容易。

大规模重构按多个可独立验证的小阶段完成，不一次性重写。本文仅制定计划，未授权或实施其中的代码改动。

配套文档：

- [重复逻辑与函数抽取建议](repeated_logic_review.md)
- [大规模重构测试文件计划](refactor_test_plan.md)
- [项目基本准则](SupremePrinciple.md)

## 范围与兼容约束

主要范围：MavKit、行为树节点、MaxtCore、任务 XML/launch、快速任务工具、视觉与协同脚本，以及相应测试和构建安装配置。

默认保持 ROS 1 Noetic、BehaviorTree.CPP v3、现有节点注册名、XML 端口、参数路径、话题/服务/Action 名称及消息定义。保留现有启动方式与脚本入口。ROS 2 迁移、更换行为树版本、改进控制算法和重新设计 TUI 不包含在本计划中。

遵循最小修改、复用已有函数、必要注释和同步 README；不修改 `_guide.md`。修改行为必须与结构重构分开提交，并说明触发条件和前后差异。

## 目标结构与职责

以下是职责边界，不要求立即为每项建立新类或新库。优先保留现有公开入口，内部逐步委托。

| 模块 | 目标职责 | 不承担的职责 |
| --- | --- | --- |
| MaxtCore | 初始化、节点注册、树加载、tick、任务状态发布 | 控制算法与具体飞行策略 |
| MavKit 外观接口 | 为节点提供稳定的状态查询和控制入口 | 各任务的状态机 |
| MAVROS 通信部分 | 订阅与状态快照、服务请求、设点定时发布 | 任务成功/失败判断 |
| 设点与轨迹部分 | 消息构造、参考 P/V/A、减速和接管过渡 | ROS 服务调用、音频和黑板 |
| 行为树节点 | 端口读取、任务状态推进、完成/失败/halt | 重复的底层消息拼装 |
| 配置与坐标工具 | 明确单位、坐标语义及模块配置 | 隐式改变其他模块参数 |
| Python 任务工具 | 任务模型、XML 生成、监看、界面分别组织 | 飞控指令执行 |
| Python 视觉/小车工具 | 算法与 ROS 适配分别组织 | 跨模块共享不必要的全局状态 |

避免建立一个包含参数、日志、超时、Action、控制和音频的万能节点基类。仅对真实重复且语义一致的操作建立公共函数。

## 阶段 0：建立基线与确定行为契约

**工作**

1. 记录当前提交、工作区改动、依赖版本、构建命令、主要启动命令及现有测试结果；已有未提交改动不覆盖、不混入重构。
2. 盘点当前编译和运行引用，区分实际模块与旧头文件、旧脚本；根据引用证据决定后续处理，暂不删除。
3. 建立 `docs/behavior_contracts.md`：记录端口、ROS 参数、坐标/单位、时间源、失败及 halt 语义。
4. 将可疑行为记录到 `docs/refactor_decisions.md`，包含当前行为、期望、测试与处理决定。

**优先确认项**

- Nav 相对 home 的输入与 CapturePose 输出组合，非零起点是否重复偏移。
- 标定后的工程坐标、MAVROS 本地坐标、UGV 目标坐标之间的约定。
- Nav 末端 3 秒后强制成功。
- TouchDown 全局超时与 DISARM 阶段确认/重试的关系。
- Guidance 丢失目标、跟踪计时和 Action 结束的语义。
- 普通顺序树失败后跳过降落，与协同树容错返航的区别。
- 曲线速度/加速度参数属于时长估算，不能误声明为严格全程限幅。

**完成条件**：现有测试结果可复现；待确认行为被明确列出，未确认项不在结构重构中静默改变。

## 阶段 1：先建立重构保护测试

依照测试计划完成 P0，搭建假 MAVROS、可控 Action 对端、消息收集和有界等待设施。接入 catkin 测试目标，保留现有 Python 与 XML 流程测试。

首先保护数学工具、坐标转换、MavKit 发布和过渡、起降、导航及任务 XML 契约。通过真实 ROS 对端测试当前具体 MavKit，不为方便测试先大改业务接口。

**完成条件**：P0 在独立 ROS master 下稳定通过；测试无需实机、桌面或人工操作；失败日志能指出场景、输入和观测输出。

**依赖**：阶段 0。后续每个模块修改前补齐其对应 P1/P2 测试。

## 阶段 2：消除局部重复

按小提交依次处理：

1. yaw 转四元数的公共函数。
2. 固定位置悬停消息构造，复用 Hover 和 UgvCowork。
3. TouchDown 内进入上锁阶段的共同动作。
4. 圆周 PVA 设点组装和位置误差计算；优先复用已有到达判断。
5. 起降竖直速度消息构造，仅在航向策略已明确后统一。

新增文件可采用 `include/maxt_pkg/setpoint_tools.hpp`，用于纯消息构造；小函数放在已有合理位置也可，不为目录整齐强制搬迁。

**边界**：消息构造与控制模式切换分离；保留掩码、航向、时间戳及坐标行为。局部函数不引入 ROS 查询或锁等隐藏副作用。

**完成条件**：相关节点测试通过；最终发布消息与基线一致；未扩展到无关模块。

## 阶段 3：整理 MavKit 控制内核

这是风险最高的阶段，拆为三个独立步骤。

### 3.1 明确状态与锁边界

- 记录回调线程、BT 线程和定时器访问的数据及锁归属。
- 保留线程安全查询；对确实需要同一时刻 pose/twist/state 的操作提供一致快照。
- 明确公开加锁入口和内部已持锁函数，防止递归加锁。
- 保持 ROS 服务调用与长耗时操作不占用控制状态锁；任何调整先通过行为测试确认。

### 3.2 统一设点接管

- 增加表达“写入新目标并接管 RAW_CTRL”的接口。
- 保留仅更新原始目标的接口，避免每次更新重新启动过渡。
- 集中模式切换规则，记录 STANDBY、HEARTBEAT、CONTROL、RAW_CTRL、CURVE_CTRL、SLOW_DOWN 的转换条件。
- 默认 yaw、标定变换与时间戳各只在明确位置处理，避免重复转换。

### 3.3 分离参考轨迹计算

- 先提取三轴曲线边界装配和初始化。
- 再按需要建立 `ReferenceTrajectory` 一类的内部组件，接收显式时间和边界，输出参考 P/V/A。
- MavKit 继续负责发布与协调，保留现有外观接口；纯轨迹组件不读取 ROS 参数或调用服务。
- 不同时更换五次曲线算法、时长公式或控制参数。

**完成条件**：所有模式及中断/接管测试通过；重复停止不重计时；参考状态连续；BT 停止 tick 时定时发布仍符合契约。随后运行相关 SITL 轨迹验收。

## 阶段 4：统一行为树节点的组织方式

保持每个节点独立文件，统一为清晰的端口、配置读取、启动、运行、结束和中断逻辑，但不要求状态机具有同样阶段。

建议顺序：Hover/WaitStep → ConnectCheck/CapturePose/FoundCheck → Nav/Round → Takeoff/TouchDown → Guidance/UgvCowork。

- 端口读取与控制配置读取分开；必要时使用模块局部配置结构，不引入通用配置框架。
- 成功、失败和 halt 的资源清理在节点内部集中；保留 Nav 减速和协同跟随不抢占飞控等差异。
- 明确重新启动时重置的状态、计时和反馈快照。
- Action 取消与回调生命周期保持可验证，不直接抽成一个过度通用的 Action 基类。
- 如测试和依赖拆分确有收益，再引入最小控制接口；不一次性虚拟化 MavKit 全部方法。

**完成条件**：每个节点的成功、失败、超时、halt、重复启动测试齐全；真实协同 XML 与节点集成测试同时通过。

## 阶段 5：任务编排与核心执行器

- 视重复程度抽取相同构造签名的注册辅助函数；保留特殊构造节点的显式注册。
- 将 mission_status 序列化从执行循环中分离，维持 JSON 字段和最终状态行为。
- 检查退出时树 halt、spinner、Action 和对象销毁顺序；需要改变当前行为的部分单独列为修复。
- 通过真实 BT 工厂获取节点端口契约，逐步替换测试中依赖 C++ 文本解析的方式。
- 检查区域子树实例的黑板隔离、结果值和 halt 传播。
- 仅在重复且行为相同的 launch 段落之间提取公共入口，保留参数默认值与转发规则。

**完成条件**：任务 XML 全部可构造；流程测试与状态发布测试通过；所有既有 launch 使用方式得到验证。

## 阶段 6：Python 工具模块化

先补齐对应工具测试，再分批拆分。

| 对象 | 拆分方向 | 保留约束 |
| --- | --- | --- |
| `script/fast_mission/fast_mission.py` | 任务定义/XML 生成、任务模型、参数编辑、监看、TUI 绘制 | 原 CLI/TUI 命令、离线可用、任务文件格式 |
| `script/aruco_center.py` | 图像检测计算与 ROS 消息/Action 适配 | 字典与 ID 配置、像素误差方向、话题名 |
| `script/ugv_sim.py` | 运动更新与 Action/绘图 | 抢占、取消、墙钟推进及既有目标语义 |
| `script/ugv_controller.py` | 配置解析与顺序执行 | 失败停止、退出取消自身任务 |

共享 YAML 读取等小工具只在收益明确时抽取。拆分后同步 Python 安装与导入路径，验证源码运行、rosrun 和安装空间运行；不能只保证开发目录能启动。

**完成条件**：原有工具测试和新测试通过，用户入口与生成文件保持兼容。

## 阶段 7：构建清理与最终验收

- 明确并统一实际 C++ 标准配置，整理目标级依赖与导出依赖。
- 核对头文件、库、Python 模块、launch/config/action/srv 和模型资源的安装完整性。
- 旧代码仅在确认无内部/外部使用后单独处理，删除提交与功能重构分开。
- 验证干净构建、测试目标及安装空间运行。
- 执行 SITL：基础起降导航、区域遍历、视觉接管、协同返航；至少覆盖非零 home 与非零标定角。
- 更新 README 的架构、配置、测试与运行说明，并标记决策清单的处理结果。

**完成条件**：自动化测试通过；关键 SITL 场景满足已定义容差；接口兼容差异全部有记录；没有依赖工作区残留文件才能成功的构建或运行流程。

## 提交与回退方式

每个提交尽量只属于一种类型：补测试、抽取公共函数、移动职责、修复行为、清理废弃代码。每个阶段保持可构建、可运行，记录对应测试结果。

重构提交若出现接口变化、测试回退、设点不连续或不稳定超时，应停止扩大范围，先定位或回退该提交。回退以独立提交为单位，保留用户其他改动，不使用整体工作区重置。

不长期维护两套控制路径。确需临时适配时，说明用途、删除条件和测试覆盖，完成迁移后及时移除。

## 建议的第一批工作

1. 完成行为契约和疑点登记，运行现有测试建立基线。
2. 增加坐标转换、五次曲线和 PID 单元测试。
3. 建立假 MAVROS，增加 MavKit 设点、导航和起降基线测试。
4. 在测试保护下抽取 yaw 转换和固定位置悬停消息。
5. 验证这批变更后，再进入 MavKit 状态和轨迹拆分。

不预估固定工期：阶段 0/1 的基线结果、现有依赖可用性及待确认行为数量会直接影响工作量。按上述验收门槛推进，比同时启动全部模块更容易定位问题和回退。
